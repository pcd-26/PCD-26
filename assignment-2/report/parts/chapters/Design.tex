\section{Design}

\subsection{Overview}

The design keeps the three implementations \textbf{intentionally separate}.
This follows the assignment requirement: each version should highlight its own
programming discipline instead of sharing a common traversal engine.

\begin{itemize}
  \item \textbf{Virtual threads}: imperative recursion and one task per
  directory;
  \item \textbf{Reactive}: an \texttt{Observable<File>} stream and an
  immutable accumulator;
  \item \textbf{Event-loop}: Vert.x callbacks and asynchronous file
  system operations.
\end{itemize}

The CLI and GUI can select the implementation at runtime. The public result is
always the same \textbf{\texttt{FSReport}} model, while the scheduling and
traversal strategy change underneath.

\subsection{Library API}

The asynchronous operation \textbf{\texttt{getFSReport}} is exposed by the
three implementation classes:

\begin{itemize}
  \item \texttt{EventLoopFSStat.getFSReport(...)} starts a Vert.x scan and
  returns an \texttt{FSReportJob} cancellation handle;
  \item \texttt{ReactiveFSStat.getFSReport(...)} returns an
  \texttt{Observable<FSReport>}, i.e. a stream of partial and final reports;
  \item \texttt{VirtualThreadsFSStat.getFSReport(...)} starts a virtual-thread
  scan and returns an \texttt{FSReportJob} cancellation handle.
\end{itemize}

The imperative versions use an \textbf{\texttt{FSReportListener}} for progress,
completion, and errors. The reactive version uses the standard RxJava signals:
\textbf{\texttt{onNext}}, \textbf{\texttt{onComplete}}, and
\textbf{\texttt{onError}}. In all cases, the logical result is the same: a
sequence of progress reports and a final filesystem statistics report.

\subsection{Virtual Threads Strategy}

The Virtual Threads implementation keeps the code close to a normal recursive
filesystem walk. Every subdirectory is submitted as a separate virtual-thread
task, so many blocking filesystem operations can coexist without requiring a
large pool of platform threads.

The strategy is based on:

\begin{itemize}
  \item \textbf{scheduling}: recursive task submission on a virtual-thread
  executor;
  \item \textbf{completion}: an \texttt{AtomicInteger} task counter and a
  \texttt{CountDownLatch};
  \item \textbf{state}: \texttt{LongAdder} counters for total files and bands;
  \item \textbf{cycles}: canonical paths are used to avoid revisiting the same
  directory;
  \item \textbf{updates}: a periodic reporting thread emits intermediate
  snapshots.
\end{itemize}

This version is the most direct one to read: the control flow remains
imperative, while virtual threads make the blocking filesystem calls cheap to
schedule.

\subsection{Reactive Strategy}

The Reactive version represents the traversal as a stream. The directory walk
emits regular files through an \texttt{Observable<File>}; the Rx pipeline then
turns that stream into report snapshots.

The strategy is based on:

\begin{itemize}
  \item \textbf{scheduling}: the blocking walk is subscribed on
  \texttt{Schedulers.io()};
  \item \textbf{state}: an immutable \texttt{ReactiveScanState} accumulator;
  \item \textbf{accumulation}: \texttt{scan(initial, ...)} creates a new state
  after each emitted file;
  \item \textbf{updates}: \texttt{sample(...)} limits progress reports to about
  one every 100 ms;
  \item \textbf{cancellation}: disposing the subscription stops further
  emissions.
\end{itemize}

The directory walk is deliberately sequential inside the observable generator.
The goal is to keep the reactive control flow explicit instead of turning this
version into another task-based implementation.

\subsection{Event-Loop Strategy}

The Event-Loop version uses Vert.x callbacks and asynchronous filesystem
operations. The event loop receives completion events from directory reads,
file-property reads, timers, and blocking validations delegated with
\texttt{executeBlocking}.

The strategy is based on:

\begin{itemize}
  \item \textbf{scheduling}: asynchronous \texttt{readDir()} and
  \texttt{props()} calls;
  \item \textbf{state}: shared counters, a cancellation flag, and a visited
  canonical-path set;
  \item \textbf{completion}: a pending-task counter detects when all callbacks
  have drained;
  \item \textbf{updates}: a Vert.x periodic timer emits progress snapshots;
  \item \textbf{safety}: an atomic closed flag prevents closing Vert.x twice.
\end{itemize}

This version has the most coordination code, but it best expresses the
event-loop rule: callbacks continue the computation, and the event loop is not
blocked by filesystem work.

\subsection{Progress, Cancellation, and Interfaces}

The three implementations expose the same user-visible behaviour, but
cancellation is implemented differently:

\begin{itemize}
  \item \textbf{Virtual threads}: set a cancellation flag, interrupt the
  reporter, and
  stop the virtual-thread executor;
  \item \textbf{Reactive}: dispose the subscription, after which the generator
  observes
  \texttt{isDisposed()} and stops emitting files;
  \item \textbf{Event-loop}: set a cancellation flag, cancel the progress
  timer, and close
  the Vert.x instance when pending callbacks have drained.
\end{itemize}

Progress is deliberately throttled to about one report every 100 ms. This keeps
the CLI readable and avoids flooding the Swing Event Dispatch Thread.

The \textbf{CLI} accepts the directory, \texttt{MaxFS}, \texttt{NB}, an
optional size unit, and an optional paradigm selector
(\texttt{vt}, \texttt{rx}, or \texttt{loop}). The \textbf{GUI} exposes the same
parameters and adds start/cancel controls. GUI updates are marshalled back onto
the Swing EDT with \texttt{SwingUtilities.invokeLater}.
