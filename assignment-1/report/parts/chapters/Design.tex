\section{Design}

\noindent
The three implementations share the same game logic and differ only in their runtime organization.

\subsection{Project architecture}

The project architecture is built around three stable elements:

\begin{itemize}
    \item the \textbf{shared game model};
    \item the \textbf{controller/runtime};
    \item the \textbf{view}.
\end{itemize}

The controller/runtime publishes \textbf{immutable snapshots} after each tick, and the view consumes only those snapshots. This keeps rendering separate from simulation updates and prevents the GUI from observing half-finished state changes.

The \textbf{sequential} version is the reference architecture. A single execution flow reacts to the input callbacks, advances the physics, updates the logical state, and publishes the resulting snapshot. This version defines the expected semantics and provides the baseline used to evaluate the concurrent versions.

\subsection{Designing the concurrent solution}

Each tick has a \textbf{parallelizable} part and a \textbf{serial} part. The \textbf{parallelizable} and \textbf{non parallelizable} parts of the system were analysed separately.

\begin{itemize}
    \item \textbf{Parallelizable}: local physics work over independent chunks of the simulation;
    \item \textbf{Not parallelizable}: command processing, sparse-delta merge, score updates, game-over checks, and snapshot publication;
\end{itemize}

The design goal is to keep one authoritative game protocol while letting the heavy local work run in parallel. The coordinator owns the tick order and the rule-level transitions; worker threads or tasks operate only inside bounded physics phases, either on disjoint ranges or on private accumulators.

\subsection{Platform-thread version}

The platform-thread version uses one \textbf{controller thread} plus long-lived \textbf{worker platform threads} inside the physics engine. The controller keeps ownership of the global progression of the match, while workers handle the \textbf{parallelizable physics work}. This matches the actual implementation: commands are queued in the shared \textbf{commands} monitor, executed on the controller thread, physics workers stay confined to private chunks or private collision accumulators, and the controller publishes the \textbf{immutable snapshot} after each tick.

\begin{itemize}
    \item the controller executes pending commands and advances the global tick;
    \item workers handle bounded pieces of the physics workload;
    \item the physics engine keeps the \textbf{merge} phase serialized and applies merged deltas either serially or in parallel over disjoint touched-ball indexes;
    \item the bot runs on a separate platform thread and submits commands to the shared \textbf{commands} queue.
\end{itemize}

\subsection{Task-based version}

The task-based version keeps the same \textbf{controller-driven game protocol}, but it schedules the controller tick with a \textbf{single-thread scheduled executor}. The parallelizable physics work is expressed as \textbf{executor tasks}, and the controller waits on \textbf{Futures} before merging the partial results and publishing the next snapshot. The bot is separate from the physics tasks: it runs on a dedicated single-thread executor and submits commands to the shared \textbf{commands} queue. The implementation also keeps a \textbf{fast path} for workloads below the parallelization threshold or with a single worker, where the range decomposition produces one range that is executed directly.

\begin{itemize}
    \item the controller tick is scheduled periodically by the executor;
    \item tasks compute the parallelizable physics work independently;
    \item the controller merges the partial results and publishes the next snapshot only after the join barrier;
    \item the bot runs on a dedicated single-thread executor and still submits commands to the shared \textbf{commands} queue.
\end{itemize}

\subsection{Why this design works}

This design keeps \textbf{one authoritative game flow} while moving the expensive physics work into \textbf{parallel worker phases}. The controller is the only component that executes commands, advances the tick protocol, updates scores and game-over state, and publishes snapshots. Physics workers or tasks operate only inside that tick on disjoint ranges or private accumulators, and the deterministic merge/apply order keeps the outcome stable. As the number of balls grows, the parallel portion grows with it, and the concurrent versions can exploit the available cores more effectively without exposing the view to partial updates.
