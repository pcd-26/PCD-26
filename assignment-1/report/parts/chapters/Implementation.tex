\section{Implementation}

\subsection{Implementation overview}

The final implementation is organized around a single path:

\begin{center}
\texttt{PooolApplication $\rightarrow$ GameLoop $\rightarrow$ GameModel $\rightarrow$ Board $\rightarrow$ PhysicsStepper}.
\end{center}

The sequential, platform-thread, and task-based programs reuse the same game
rules and board. The two concurrent programs also reuse the same application
lifecycle, controller tick, command monitor, snapshot protocol, and parallel
physics algorithm.

\subsection{Application and runtime}

\texttt{ThreadedPoool} and \texttt{TaskBasedPoool} are small entry points that
construct their runner and delegate the GUI lifecycle to
\texttt{PooolApplication}. The runners implement the common
\texttt{GameRuntime} interface.

The central runtime class is \texttt{GameLoop}. One tick has only three steps:

\begin{lstlisting}[style=codestyle,caption={Shared single-writer game tick},label={lst:shared-game-loop}]
public void tick(long tickMillis) {
    commands.drain(game);
    if (!game.snapshot().isFinished()) {
        game.step(tickMillis);
    }
    publishSnapshot();
}
\end{lstlisting}

\texttt{ThreadedGameRunner} invokes this method from one explicitly created
platform thread. \texttt{TaskBasedGameRunner} schedules the same method on a
single-thread \texttt{ScheduledExecutorService}. This removes duplicated game
protocols while keeping both execution styles visible.

\subsection{Asynchronous commands}

\texttt{CommandMailbox} is the custom monitor between producers and the
single-writer controller. Swing and \texttt{BotAgent} submit a model operation
and receive a receipt. The controller drains operations in FIFO order. On
shutdown, pending and future commands complete with their rejected result.

The mailbox means that neither Swing nor the bot receives a reference that can
mutate \texttt{GameModel}. They only express an intention; mutation happens on
the controller owner.

\subsection{Domain ownership}

\texttt{GameModel} owns scores, countdown, shot eligibility, winner, and match
termination. \texttt{Board} owns balls, holes, boundaries, pocket state, and
physical contact events. \texttt{RuntimeGameSnapshot} combines an immutable
logical snapshot with copied rendering data, so the GUI never reads a partially
updated board.

\subsection{One parallel physics algorithm}

\texttt{ParallelPhysicsEngine} contains the complete concurrent algorithm. The
public \texttt{ThreadedPhysicsEngine} and \texttt{TaskBasedPhysicsEngine} are
small facades that select a \texttt{RangeScheduler}:

\begin{itemize}
    \item \texttt{PlatformThreadRangeScheduler}: reusable
          \texttt{PhysicsWorker} platform threads and
          \texttt{WorkerCompletionMonitor};
    \item \texttt{ExecutorRangeScheduler}: a fixed \texttt{ExecutorService}
          and \texttt{Future} barrier.
\end{itemize}

The kernel delegates only independent contiguous ranges:

\begin{lstlisting}[style=codestyle,caption={The concurrency seam inside the shared kernel},label={lst:range-scheduler-seam}]
var stats = scheduler.execute(itemCount,
        (from, to, workerIndex) -> rangeTask.run(from, to, workerIndex));
\end{lstlisting}

The platform scheduler assigns chunks directly to its workers:

\begin{lstlisting}[style=codestyle,caption={Platform-thread range dispatch},label={lst:platform-range-dispatch}]
workers[workerIndex].assign(
        () -> operation.run(rangeStart, rangeEnd, assignedWorker),
        completion);
completion.await();
\end{lstlisting}

The Executor scheduler expresses the same range as a task:

\begin{lstlisting}[style=codestyle,caption={Executor range dispatch},label={lst:executor-range-dispatch}]
futures.add(executor.submit(
        () -> operation.run(rangeStart, rangeEnd, assignedWorker)));
for (var future : futures) {
    future.get();
}
\end{lstlisting}

\subsection{Physics phases}

Each fixed sub-step executes:

\begin{enumerate}
    \item active-ball collection;
    \item parallel movement integration over disjoint ranges;
    \item serialized hole interactions;
    \item parallel construction of private spatial grids;
    \item deterministic grid merge and cell ordering;
    \item parallel collision-contribution calculation into private sparse accumulators;
    \item sorted contact recording and merged-delta commit.
\end{enumerate}

Workers never directly update scores or remove balls. Collision contributions
are calculated against the same tick-start state, then merged in a stable
order. This preserves deterministic seeded results across both schedulers.

\subsection{Small-work fast path}

The Executor scheduler executes ranges smaller than 256 items inline. The
shared kernel also applies small collision-delta sets sequentially. These paths
avoid task and synchronization overhead while leaving large workloads
parallel.

\subsection{Delivery boundary}

Benchmark code remains compiled for scripts and report generation but is
excluded from the packaged game JAR. Sketch artifacts remain under
\texttt{reference/}. The playable artifact therefore contains only the game,
runtime, physics, and view concepts described above.
