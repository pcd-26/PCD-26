\section{Problem Analysis}

The core problem is coordinating multiple asynchronous activities around one
\textbf{mutable game state}. During a tick, balls move, collide, enter holes,
update scores, and may terminate the match. These effects must appear as one
coherent state transition even if input handling, bot behaviour, rendering,
and physics computation progress concurrently.

\subsection{Concurrent activities and shared state}

The system contains four activities with different timing requirements:

\begin{itemize}
    \item the \textbf{game controller} advances the simulation periodically;
    \item the \textbf{graphical interface} receives human input and updates the displayed state;
    \item the \textbf{bot} independently decides when to shoot;
    \item the \textbf{physics workers} cooperate within a simulation tick.
\end{itemize}

The shared state includes ball positions and velocities, pocketed balls,
scores, turn eligibility, and match termination. Without a strict ordering, a
race could apply input in the wrong phase, score a ball twice, or expose a
partially updated board to the view.

For this reason, input is treated as an \textbf{asynchronous request} and
rendering reads only a stable copy of the last completed state.

\subsection{Physics dependencies and available parallelism}

The physics workload grows with the number of balls. Movement has linear cost,
while naive collision detection compares every pair and requires $O(n^2)$
tests. For large workloads, collision detection dominates the tick duration, so
executing the full simulation on the UI thread would make the interface
unresponsive.

Not every operation in a tick is independent. Movement must finish before hole
handling and collision processing. Removing pocketed balls changes the active
set. Collision effects must be combined before the new state becomes visible.
The step must therefore be organized as \textbf{ordered phases} separated by
completion barriers.

Useful \textbf{data parallelism} is available within some phases. Distinct ball
ranges can be moved independently. Separate portions of the spatial partition
can be built concurrently. Collision candidates can also be examined by
different workers.

Collision resolution is more delicate because several contacts may affect the
same ball. The key distinction is therefore between \textbf{parallel work on
private or disjoint data} and \textbf{ordered application to shared state}.

\subsection{Correctness requirements}

The concurrent implementations must preserve the semantics of the sequential
baseline. Given the same initial configuration and input sequence, the
execution strategy must not change ball state, scoring, or the winner. This is
especially important for floating-point collision calculations. A different
accumulation order can produce diverging results over time.

The relevant correctness goals are:

\begin{itemize}
    \item \textbf{Safety}: only completed ticks are published and each accepted command is processed at most once;
    \item \textbf{Determinism}: scheduling does not change the observable game result;
    \item \textbf{Responsiveness}: input and rendering do not depend on long physics computations;
    \item \textbf{Termination}: threads, tasks, and pending requests are released correctly at shutdown.
\end{itemize}

\subsection{Performance and scalability}

Parallel execution is useful only when its benefit exceeds
\textbf{partitioning, scheduling, synchronization, and merge overheads}. Small
workloads may run faster sequentially. Large workloads provide enough
independent work to amortize these costs.

The two concurrent versions solve the same problem through different execution
models. Their evaluation therefore requires a \textbf{common sequential
baseline}, equivalent workloads, and configurable parallelism. Elapsed time
alone is not sufficient. Speedup as the workload grows and speedup as the
worker count changes are needed to explain whether the available cores are used
effectively and where the implementation reaches saturation.
