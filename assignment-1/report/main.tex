\section{Introduction}

Assignment 1 requires three execution strategies for \emph{Poool}: a sequential baseline, a platform-thread implementation, and a task-based implementation built on the Executor framework. The brief also asks for performance measurements and model checking with Java PathFinder (JPF).

This report presents the implemented strategies:

\begin{itemize}
    \item \textbf{Sequential baseline}: single-thread reference execution;
    \item \textbf{Platform-thread version}: controller-led platform-thread architecture with long-lived workers;
    \item \textbf{Task-based version}: concurrent execution using the Executor framework.
\end{itemize}

All three launchers reuse the same game rules.

\section{Problem Analysis}

The main difficulty is the management of a shared mutable board under asynchronous input and a non-trivial simulation workload. During each tick, many balls move, collide, and change status, so the implementation must preserve deterministic state transitions while still allowing useful concurrency.

\begin{itemize}
    \item \textbf{Computational cost}: collision detection and resolution become the dominant cost as the number of balls increases;
    \item \textbf{Shared state}: the board must be updated consistently even when multiple events are active;
    \item \textbf{Asynchronous input}: human and bot actions arrive while the simulation is running;
    \item \textbf{Determinism}: concurrency must not alter the logical outcome of the match;
    \item \textbf{Responsiveness}: the interface must remain reactive while the simulation progresses.
\end{itemize}

The concurrent part of the assignment is therefore a matter of separating the simulation work that can be parallelized from the coordination that must remain serialized. The implementation must preserve a consistent global view of the match while keeping the simulation efficient.

\textbf{The objective} is to \textbf{exploit parallelism} while preserving \textbf{coherence} and \textbf{determinism}.

\section{Design}

\noindent
The design is based on separation of responsibilities. The model contains the game rules and state, while the rest of the architecture is organized around a controller/runtime and a view.

The three implementations share the same game logic and differ only in their runtime organization.

\subsection{Project architecture}

The project architecture is built around three stable elements:

\begin{itemize}
    \item the \textbf{shared game model};
    \item the \textbf{controller/runtime};
    \item the \textbf{view}.
\end{itemize}

The controller/runtime publishes \textbf{immutable snapshots} after each tick, and the view consumes only those snapshots. This keeps rendering separate from simulation updates and prevents the GUI from observing half-finished state changes.

The same structure is reused by the \textbf{sequential}, \textbf{platform-thread}, and \textbf{task-based} launchers, while only the \textbf{execution policy} changes.

The \textbf{sequential} version is the reference architecture. A single execution flow reacts to the input callbacks, advances the physics, updates the logical state, and publishes the resulting snapshot. This version defines the expected semantics and provides the baseline used to evaluate the concurrent versions.

\subsection{Platform-thread version}

The platform-thread version uses one \textbf{controller thread} plus long-lived \textbf{worker platform threads} inside the physics engine. The controller keeps ownership of the global progression of the match, while workers handle the \textbf{parallelizable physics work}. This matches the actual implementation: commands are queued in the shared \textbf{commands} monitor, executed on the controller thread, physics workers stay confined to private chunks, and the controller publishes the \textbf{immutable snapshot} after each tick.

\begin{itemize}
    \item the controller executes pending commands and advances the global tick;
    \item workers handle bounded pieces of the physics workload;
    \item the physics engine keeps the \textbf{merge} and \textbf{apply} phases serialized;
    \item the bot runs on a separate platform thread and submits commands to the shared \textbf{commands} queue.
\end{itemize}

\subsection{Task-based version}

The task-based version keeps the same \textbf{single-writer rule}, but it schedules the controller tick with a \textbf{single-thread scheduled executor}. The parallelizable physics work is expressed as \textbf{executor tasks}, and the controller waits on \textbf{Futures} before merging the partial results and publishing the next snapshot. The bot is separate from the physics tasks: it runs on a dedicated single-thread executor and submits commands to the shared \textbf{commands} queue. The implementation also keeps a \textbf{fast path} for workloads below the parallelization threshold or with a single worker, where the range decomposition produces one range that is executed directly.

\begin{itemize}
    \item the controller tick is scheduled periodically by the executor;
    \item tasks compute the parallelizable physics work independently;
    \item the controller merges the partial results and publishes the next snapshot only after the join barrier;
    \item the bot runs on a dedicated single-thread executor and still submits commands to the shared \textbf{commands} queue.
\end{itemize}

\subsection{Why this design works}

This design keeps \textbf{one authoritative state} while moving the expensive physics work into \textbf{parallel worker phases}. The controller is the only component that works on the shared state, so it runs the serial phases and keeps the outcome \textbf{deterministic}. As the number of balls grows, the parallel portion grows with it, and the concurrent versions can exploit the available cores more effectively without exposing the view to partial updates.

\section{Implementation}

\subsection{Implementation overview}

The implementation mirrors the design: the same game rules are reused by all launchers, while the execution strategy changes between the sequential, \textbf{platform-thread}, and \textbf{task-based} versions. The code is split into the \textbf{model}, the \textbf{physics engines}, the \textbf{runtime helpers}, and the \textbf{Swing view}, so the responsibilities stay visible in the source tree.

The concurrent engines follow the same rule: the \textbf{controller} assigns work, the workers process \textbf{private slices}, and the controller merges the partial results into one \textbf{authoritative state}. The work is split into \textbf{contiguous ranges}, then into \textbf{private center-cell grids}, and finally into a \textbf{deterministic join} and commit phase.

The difference between the two concurrent versions is the execution style. The threaded engine uses long-lived \textbf{platform workers} and a completion monitor; the task-based engine submits the same ranges to an \textbf{executor} and waits on \textbf{Future}s. In both cases, the local loop stays sequential inside each worker, and the task-based engine keeps a small-workload \textbf{fast path} when parallel decomposition is not worth the overhead.

\begin{itemize}
    \item \textbf{\texttt{pcd.poool.model}}: game rules, board state, and immutable snapshots;
    \item \textbf{\texttt{pcd.poool.model.physics}}: sequential, threaded, and task-based physics engines, plus shared physics helpers;
    \item \textbf{\texttt{pcd.poool.runtime}}: command submission and snapshot publication helpers;
    \item \textbf{\texttt{pcd.poool.threaded}} and \textbf{\texttt{pcd.poool.taskbased}}: concurrent runners;
    \item \textbf{\texttt{pcd.poool.view}} and \textbf{\texttt{pcd.poool.view.board}}: rendering and input handling.
\end{itemize}

The three public entry points are \texttt{SequentialPoool}, \texttt{ThreadedPoool}, and \texttt{TaskBasedPoool}. They build the corresponding runtime, connect it to the view, and keep the GUI loop separate from the simulation logic.

\subsection{Core classes}

The core classes reflect the separation between rules, mutable state, execution, and publication:

\begin{itemize}
    \item \texttt{GameModel} (\path{pcd.poool.model.game}): game rules, scoring, end-game conditions, and logical snapshots;
    \item \texttt{Board} (\path{pcd.poool.model.physics.common}): mutable physical state, advanced through a \texttt{PhysicsStepper};
    \item \texttt{SequentialPhysicsEngine}, \texttt{ThreadedPhysicsEngine}, and \texttt{TaskBasedPhysicsEngine} (\path{pcd.poool.model.physics.sequential}, \path{pcd.poool.model.physics.threaded}, \path{pcd.poool.model.physics.taskbased}): sequential, platform-thread, and executor-based physics steps;
    \item \texttt{ThreadedGameRunner} and \texttt{TaskBasedGameRunner} (\path{pcd.poool.threaded}, \path{pcd.poool.taskbased}): command draining, controller ticks, and snapshot publication;
    \item \texttt{RuntimeGameSnapshot} (\path{pcd.poool.runtime}): immutable data consumed by the view;
    \item \texttt{CommandQueueMonitorSupport} and \texttt{SnapshotStoreSupport} (\path{pcd.poool.runtime}): monitor-based command and snapshot coordination.
\end{itemize}

\subsection{Sequential implementation}

The sequential launcher is intentionally direct: one loop advances the simulation, updates the view model, and renders the frame. The game model and the view share the same object graph, but the simulation still remains easy to reason about because everything happens in order.

The helper \texttt{advanceGame} only guards the finished-state check: \texttt{GameModel.step()} advances the board through \texttt{Board.updateState()}, then consumes score events and refreshes the game status.

\begin{lstlisting}[style=codestyle,caption={Sequential main loop},label={lst:sequential-main-loop}]
var game = gameRef.get();
long elapsedMillis = Math.max(PhysicsDefaults.FIXED_STEP_MILLIS, now - lastUpdateTime);
lastUpdateTime = now;

advanceGame(game, elapsedMillis);
if (game.canBotShoot()) {
    if (botAimStartedAt == 0) {
        botAimStartedAt = now;
    } else if (now - botAimStartedAt >= BOT_THINK_TIME_MILLIS) {
        game.shootBot();
        viewModel.clearShotPreview(Player.BOT);
        botAimStartedAt = 0;
    }
} else {
    viewModel.clearShotPreview(Player.BOT);
    botAimStartedAt = 0;
}

renderedFrames++;
int currentFramesPerSecond = getCurrentFPS(renderedFrames, startTime, now);
viewModel.update(game.board(), game.snapshot(), currentFramesPerSecond);
updateBotShotPreview(game, viewModel, botAimStartedAt > 0);
view.render();
\end{lstlisting}

\noindent\textit{Source: \texttt{assignment-1/src/main/java/pcd/poool/SequentialPoool.java}, lines 61--82.}

This version is useful as the semantic baseline. It defines the expected behavior of the game without introducing concurrency concerns, and it also shows the minimum amount of code needed to keep the GUI responsive.

\subsection{Platform-thread implementation}

The platform-thread version introduces a controller thread plus an optional bot thread. The controller is the only thread that mutates the model, while external producers submit commands through a monitor-backed queue. The threaded physics engine is still called from the controller, so the controller remains the single point where the match advances.

\begin{lstlisting}[style=codestyle,caption={Threaded controller loop},label={lst:threaded-controller-loop}]
while (running) {
    drainPendingCommands();
    if (!game.snapshot().isFinished()) {
        game.step(config.tickMillis());
    }
    snapshots.publish(RuntimeGameSnapshot.from(game));
    sleepTick();
}
\end{lstlisting}

The key classes here are \texttt{ThreadedGameRunner} and \texttt{ThreadedPhysicsEngine}. The runner serializes the game protocol, and the threaded physics engine parallelizes the expensive simulation work internally. The most explicit handoff happens inside \texttt{runRanges()}, where the controller assigns one range of work to each worker thread.

\begin{lstlisting}[style=codestyle,caption={Range partitioning for worker assignment},label={lst:threaded-range-partition}]
int workerCount = Math.min(workers.length, itemCount);
int baseChunk = itemCount / workerCount;
int remainder = itemCount % workerCount;
int from = 0;
for (int workerIndex = 0; workerIndex < workerCount; workerIndex++) {
    int chunkSize = baseChunk + (workerIndex < remainder ? 1 : 0);
    int start = from;
    int end = start + chunkSize;
    int assignedWorker = workerIndex;
    workers[workerIndex].assign(() -> rangeTask.run(start, end, assignedWorker), completion);
    from = end;
}
\end{lstlisting}

\noindent\textit{Source: \path{ThreadedPhysicsEngine.java}, lines 544--568.}

This divides the work into contiguous index ranges of almost equal size, with the remainder distributed among the first workers. A worker does not receive spatial zones, but a contiguous slice of \texttt{activeBalls}, which it processes in order.

\begin{lstlisting}[style=codestyle,caption={Threaded handoff from controller to workers},label={lst:threaded-handoff}]
for (int workerIndex = 0; workerIndex < workerCount; workerIndex++) {
    int chunkSize = baseChunk + (workerIndex < remainder ? 1 : 0);
    int start = from;
    int end = start + chunkSize;
    int assignedWorker = workerIndex;
    workers[workerIndex].assign(() -> rangeTask.run(start, end, assignedWorker), completion);
    from = end;
}

completion.await();
\end{lstlisting}

\noindent\textit{Source: \path{ThreadedPhysicsEngine.java}, lines 562--578.}

This is the actual point where the controller passes the physics work to the worker threads. The workers run their assigned range independently, and the controller resumes only after the completion barrier has been reached. The collision phase follows the same idea: each worker computes local contributions on its own slice, builds a private spatial view, and resolves the cells it owns before the controller merges the sparse results and applies the final writes to the authoritative board.

\subsection{Task-based implementation}

The task-based version keeps the same controller-driven protocol, but the parallel physics phase is expressed as executor tasks. The runner uses a scheduled single-thread controller executor for the tick and a separate executor for the bot. The task-based physics engine still splits the active balls into contiguous ranges, but each range is submitted as a task rather than assigned to a long-lived worker thread.

\begin{lstlisting}[style=codestyle,caption={Task-based controller scheduling},label={lst:taskbased-scheduling}]
running = true;
controllerExecutor.scheduleAtFixedRate(this::tick, 0,
        config.tickMillis(), TimeUnit.MILLISECONDS);
\end{lstlisting}

\begin{lstlisting}[style=codestyle,caption={Task-based range partitioning},label={lst:taskbased-range-partition}]
int workerCount = itemCount < MIN_ITEMS_FOR_PARALLEL_RANGES ? 1 : Math.min(poolSize, itemCount);
int baseChunk = itemCount / workerCount;
int remainder = itemCount % workerCount;
var chunks = new ArrayList<RangeChunk>(workerCount);
int from = 0;
for (int i = 0; i < workerCount; i++) {
    int chunkSize = baseChunk + (i < remainder ? 1 : 0);
    int to = from + chunkSize;
    chunks.add(new RangeChunk(from, to, i));
    from = to;
}
\end{lstlisting}

\noindent\textit{Source: \path{TaskBasedPhysicsEngine.java}, lines 662--672.}

Inside the task-based physics engine, the work is partitioned into ranges and executed through futures. Tasks do the independent work, the coordinator waits, and only then are the shared updates applied. For collision detection, each task builds a private local grid, the coordinator merges those grids, sorts the packed candidate pairs, records collisions in deterministic order, and applies the accumulated deltas. The local grid is still built sequentially inside each task; the gain comes from running many task-local loops in parallel.

\begin{lstlisting}[style=codestyle,caption={Task submission and synchronization},label={lst:taskbased-futures}]
var futures = new ArrayList<Future<T>>(ranges.size());
for (var range : ranges) {
    futures.add(executor.submit(() ->
            rangeTask.run(range.fromInclusive(), range.toExclusive(),
                    range.workerIndex())));
}
for (var future : futures) {
    results.add(future.get());
}
\end{lstlisting}

Compared with the threaded implementation, the control protocol is the same at the report level. What changes is the execution style: long-lived workers on one side, scheduled tasks on the other.

\subsection{Runtime snapshots and coordination helpers}

\texttt{RuntimeGameSnapshot} is the bridge between the model and the GUI. It combines the logical \texttt{GameSnapshot} with the copied board and preview data used by the view, so rendering never needs to inspect mutable state directly.

\begin{lstlisting}[style=codestyle,caption={Runtime snapshot construction},label={lst:runtime-snapshot}]
return new RuntimeGameSnapshot(
        game.snapshot(),
        List.copyOf(board.getBalls()),
        board.getPlayerBall(),
        board.getBotBall(),
        List.copyOf(board.getHoles()),
        game.previewBotShot());
\end{lstlisting}

The concurrent runners publish those snapshots through \texttt{SnapshotStoreSupport}, which acts as a monitor around the latest immutable state. Commands follow the same idea through \texttt{CommandQueueMonitorSupport}: external threads enqueue requests, and the controller drains them sequentially.

\subsection{Implementation summary}

Overall, the implementation keeps the domain model small and central, pushes concurrency into the runtime and physics layers, and uses immutable snapshots to isolate the view. The result is a code base where the sequential, threaded, and task-based versions differ mainly in scheduling, not in game semantics.

\section{Verification and Testing}

The repository includes JUnit tests under \texttt{src/test/java/pcd/poool}. They exercise the game model, the physics engines, the runtime helpers, the concurrent runners, the view layer, and the benchmark utilities.

\subsection{JPF model checking}

The verification area contains two minimal JPF harnesses:
\path{pcd.poool.verification.jpf.ThreadedMiniHarness} and
\path{pcd.poool.verification.jpf.TaskBasedMiniHarness}. Both reuse
\path{MinimalProtocolState}, whose assertions check the actual coordination
rules of the reduced protocol:

\begin{itemize}
    \item the board cannot be owned twice at the same time;
    \item the worker/task cannot complete before board ownership is established;
    \item pending commands are drained before publication;
    \item the final state must release ownership, publish the snapshot, and reach the finished flag.
\end{itemize}

The two JPF configuration files are \texttt{threaded-minimal.jpf} and
\texttt{taskbased-minimal.jpf}. They use the same reduced setup:

\begin{verbatim}
target=pcd.poool.verification.jpf.ThreadedMiniHarness
target=pcd.poool.verification.jpf.TaskBasedMiniHarness
classpath=target/jpf-classes
search.class=gov.nasa.jpf.search.DFSearch
vm.storage.class=gov.nasa.jpf.vm.JenkinsStateSet
vm.por=true
vm.max_heap=64m
search.depth_limit=40
\end{verbatim}

The actual JPF runs were executed through the Docker helper:
\begin{verbatim}
python assignment-1/verification/jpf/run_jpf.py --docker --model threaded
python assignment-1/verification/jpf/run_jpf.py --docker --model taskbased
\end{verbatim}
Both runs completed with \texttt{no errors detected}.

\begin{itemize}
    \item \textbf{Threaded model}: \texttt{states: new=774, visited=1117, backtracked=1891, end=4}; \texttt{maxDepth=35}; \texttt{instructions=22411}.
    \item \textbf{Task-based model}: \texttt{states: new=249, visited=288, backtracked=537, end=3}; \texttt{maxDepth=34}; \texttt{instructions=16409}.
\end{itemize}

The threaded model explores a larger state space because its worker thread stays alive across the protocol steps. The task-based model is smaller because the worker is represented as a short-lived task. In both cases, JPF confirms the bounded synchronization protocol reaches completion without deadlock or assertion failure, which is exactly the level of verification this report claims \cite{clarke1999,visser2003}.

\section{Conclusions}

The delivered project satisfies the three required execution strategies while keeping the shared game semantics stable across them. The report now reflects the actual implementation flow: the controller remains the single writer, the heavy physics phases are split into worker-local chunks, and the partial results are joined before the snapshot is published.

The benchmark evidence is consistent across the two exported snapshots. For the speedup-gate workloads, both concurrent versions beat the sequential baseline once the workload reaches 1000 balls and above, and the best snapshot value in that family is the task-based run on 2500 balls at 237.5317 ms. For the scalability snapshot, the threaded engine is best at 16 workers, while the executor-based engine is best at 17 workers; neither scales linearly, and both stay far from ideal efficiency, which points to non-negligible serial work and coordination overhead.

The verification story is also bounded in a controlled way. The Petri nets explain the control protocol at the level requested by the assignment, and the JPF harnesses confirm that the reduced synchronization models terminate without deadlock or assertion failure. What these results do not prove is the full numerical physics of the game, GUI performance, or large-scale scaling beyond the measured workloads.
