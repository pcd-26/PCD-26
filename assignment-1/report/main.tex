\section{Introduction}

Assignment 1 requires three execution strategies for \emph{Poool}: a sequential baseline, a platform-thread implementation, and a task-based implementation built on the Executor framework. The brief also asks for performance measurements and verification with model checking.

The delivered project provides the following execution strategies:

\begin{itemize}
    \item \textbf{Sequential baseline}: single-thread reference execution;
    \item \textbf{Platform-thread version}: Master-Workers architecture;
    \item \textbf{Task-based version}: Executor-based parallel execution.
\end{itemize}

All three launchers reuse the same game rules.

\section{Problem Analysis}

The main difficulty is not the rule set itself, but the combination of shared mutable state, asynchronous activity, and a potentially heavy simulation workload. The board contains many balls that move, collide, and change status during the same tick, so the system must combine concurrency with deterministic state transitions.

\begin{itemize}
    \item \textbf{High computational cost}: collision detection and collision resolution dominate the simulation when the number of balls grows;
    \item \textbf{Shared mutable state}: the simulation must update the state consistently even when several events are active at the same time;
    \item \textbf{Asynchronous inputs}: human and bot actions may arrive while the simulation is running;
    \item \textbf{Deterministic behavior}: concurrency must not change the logical outcome of the match;
    \item \textbf{Responsiveness}: the interface must keep reacting while the simulation progresses.
\end{itemize}

The concurrent part of the assignment therefore becomes a question of identifying which parts of the simulation can be parallelized and which parts must remain serialized. For example, collision processing can be split across independent chunks, while processing pending commands must remain serialized because it requires a consistent global view of the match.

The key challenge is to exploit parallelism without breaking coherence.

\section{Design}

\noindent
The architecture is organized into three layers with distinct responsibilities. The shared model owns the rules and the mutable game state, the execution layer advances the match and serializes asynchronous actions, and the view layer renders immutable snapshots instead of reading the live board directly.

The main design choice is that the sequential, platform-thread, and task-based versions reuse the same semantics while changing only how work is scheduled. Command submission stays outside the model, which keeps ownership boundaries explicit throughout the concurrent protocol.

\begin{itemize}
    \item \textbf{Shared model}: owns the rules and the mutable game state;
    \item \textbf{Execution layer}: advances the match and serializes asynchronous actions;
    \item \textbf{View layer}: renders immutable snapshots instead of reading the live board directly.
\end{itemize}

\subsection{Shared model}

The shared model contains the game rules, the board state, and the physics data structures. It is the part of the system that decides what a legal state transition means, while the launcher selects the concrete physics engine used to perform the low-level step.

\subsection{Sequential baseline}

The sequential version is intentionally simple: one thread advances the match, applies the physics step, and updates the view. It is useful both as the semantic reference and as the baseline for performance comparison.

\subsection{Platform-thread runtime}

The platform-thread version adopts a Master-Workers architecture, with the controller acting as the master. The controller advances the match and publishes snapshots, while worker threads parallelize bounded physics work under controlled synchronization. This is where the design starts paying for itself, because the expensive part of the tick is split across long-lived workers while the controller keeps the authoritative state and the phase boundaries.

\subsection{Task-based runtime}

The task-based version follows the same ownership rule, but it expresses the parallel physics work as executor tasks rather than long-lived workers. Tasks compute partial results, the controller merges them, and the new state is published only after the merge. This keeps the same semantic structure as the threaded version, while making the parallel phases easier to express as bounded jobs on an executor pool.

\subsection{Parallelization strategy}

The parallelization strategy is deliberately data-oriented rather than control-oriented. The goal is not to parallelize the whole game loop, but only the physics work that can be split into independent chunks without violating single-writer ownership of the board.

The tick is therefore decomposed into phases with different coordination costs. Some phases are inherently sequential because they require a consistent global view of the match: command draining, score updates, game-over detection, snapshot publication, and the final commit of the tick. These operations stay on the controller side and are never handed to workers.

The expensive physics work is handled differently. Movement integration is partitioned over disjoint ball ranges, so each worker can update its own subset without coordinating with the others. Collision handling uses spatial ownership instead of a global candidate list: each worker builds a private local grid, the controller merges those local grids into a deterministic global structure, and only then are collisions assigned to canonical cell owners. Each worker or task computes local collision contributions and sparse deltas instead of mutating the whole board directly.

This is where most of the performance gain comes from. The design avoids the largest sources of overhead in a naive concurrent implementation: it does not let many threads write the same board state at the same time, it does not require fine-grained locks around individual balls, and it does not materialize a huge shared pair list before resolving contacts. The controller keeps the final merge, commit, and publication steps serialized, but the heavy numerical work runs in parallel on bounded chunks. The threaded version realizes this pattern with long-lived workers; the task-based version expresses the same pattern with executor tasks. In both cases, the protocol remains deterministic at phase boundaries and the work done by each participant is narrow enough to scale on large boards.

\subsection{Why this design improves performance}

The improvement is not produced by a different physics model, but by reducing coordination cost around the same physics model. The board is large enough that the cost of integrating motion and resolving collisions dominates the tick time. By splitting those phases into private chunks and postponing shared writes until the controller can merge them, the concurrent versions keep the workers busy on CPU work rather than on synchronization.

The design also keeps overhead under control for smaller workloads. When the amount of work is not large enough to justify parallel scheduling, the serialized phases remain cheap, and the system avoids introducing unnecessary contention. In practice, this is why the concurrent versions scale better as the number of balls increases: the amount of parallelizable physics work grows, while the serial coordination cost stays bounded.

\subsection{Snapshots and view data}

The view never reads the mutable board directly. Instead, the concurrent runtimes publish immutable snapshots that the GUI can consume safely, which keeps rendering detached from simulation and synchronization.

\begin{itemize}

    \item \textbf{\texttt{model/game}}: game rules and logical snapshots;

    \item \textbf{\texttt{model/physics/threaded}}: platform-thread engine;
    \item \textbf{\texttt{model/physics/taskbased}}: executor-based engine;
    \item \textbf{\texttt{runtime}}: command queues, command receipts, snapshot publication, bot coordination;
    \item \textbf{\texttt{view}}: Swing-facing rendering classes.
\end{itemize}

\subsection{Important classes}

\begin{itemize}
\item \texttt{GameModel}: owns the game rules and advances the match state;
\item \texttt{Board}: owns the mutable physical state and delegates stepping to a physics engine;
\item \texttt{PhysicsEngine}, \texttt{ThreadedPhysicsEngine}, and \texttt{TaskBasedPhysicsEngine}: implement the simulation strategies;
\item \texttt{ThreadedGameRunner} and \texttt{TaskBasedGameRunner}: coordinate asynchronous commands, controller ticks, and snapshot publication;
\item \texttt{RuntimeGameSnapshot}: packages immutable state for the GUI and asynchronous observers;
\item \texttt{CommandQueueMonitorSupport} and \texttt{SnapshotStoreSupport}: implement the monitor-based coordination used by the concurrent runtime.
\end{itemize}

\subsection{Petri nets}

The concurrent protocol can be described with an abstract Petri net. The purpose of the model is not to represent the full physics of the game, but to capture one simulation tick as a sequence of controlled phases. In particular, it records command draining, board ownership, worker execution, barrier synchronization, and snapshot publication.

The abstraction is small enough to reason about, yet expressive enough to justify the most relevant safety properties. A tick starts only when the controller owns the board and the command queue has been drained. Worker or task phases then execute on private work units or partial results, and the snapshot is published only after the merge and commit point has been reached. This captures the intended single-writer discipline of the concurrent runtime.

\begin{itemize}
    \item \textbf{What is modeled}: one simulation tick as a sequence of controlled phases;
    \item \textbf{What is not modeled}: full physics, numerical details, GUI rendering;
    \item \textbf{Phases captured}: command draining, board ownership, worker execution, barrier synchronization, snapshot publication;
    \item \textbf{Safety intuition}: the tick starts only when the controller owns the board, and publication happens only after merge and commit.
\end{itemize}

\subsection{JPF model checking}

The repository also includes minimal JPF harnesses in the verification area of the working tree. These harnesses are deliberately smaller than the production runtime: they model a controller, a bounded amount of worker or task activity, a command queue, and the publication step. The goal is to verify the control protocol, not the numerical physics engine.

The JPF models check that commands are not stranded, that publication happens after the tick is complete, and that the reduced protocol can terminate cleanly without deadlock. This is enough to validate the coordination pattern used by both the platform-thread and task-based implementations.

\begin{itemize}
    \item \textbf{Harnesses}: minimal JPF models in the verification area of the working tree;
    \item \textbf{Scope}: controller, bounded worker/task activity, command queue, publication step;
    \item \textbf{Goal}: verify the control protocol, not the numerical physics engine;
    \item \textbf{Properties checked}: no stranded commands, publication after tick completion, clean termination without deadlock.
\end{itemize}

\section{Conclusions}

The repository contains a sequential implementation, a platform-thread implementation, and a task-based implementation. The shared domain model is reused across all three.

The code uses single-writer ownership, immutable snapshots, explicit synchronization, and a separation between model and runtime.

The benchmark data in the repository shows different speedup values across workloads and worker counts.
