\section{Introduction}

Assignment 1 requires three execution strategies for \emph{Poool}: a sequential baseline, a platform-thread implementation, and a task-based implementation built on the Executor framework. The brief also asks for performance measurements and verification with model checking.

The delivered project provides the following execution strategies:

\begin{itemize}
    \item a sequential baseline;
    \item a platform-thread implementation;
    \item a task-based implementation.
\end{itemize}

All three launchers reuse the same game rules.

\section{Problem Analysis}

The board contains many small balls and two cue balls, one for the human player and one for the bot. The assignment rules are as follows:

\begin{itemize}
    \item balls move, bounce, collide, and slow down because of friction;
    \item the board has holes in the top corners;
    \item when a player puts a small ball into a hole, that player's score increases;
    \item if a cue ball enters a hole, the other player wins;
    \item human and bot actions are asynchronous.
\end{itemize}

The concurrent part of the assignment requires controlled access to shared state. In this code base, \texttt{GameModel} is the authoritative state for game progression, while the runtime layer coordinates command submission and immutable snapshot publication.

\section{Design}

The architecture is structured around three functional layers: the shared model owns the rules and the mutable game state; the execution layer advances the match and serializes asynchronous actions; and the view layer consumes immutable snapshots rather than the live board.

This separation allows the sequential, platform-thread, and task-based versions to share the same domain semantics. Command submission, snapshot publication, and physics stepping remain in distinct modules, which preserves clear ownership boundaries in the concurrent protocol.

\subsection{Shared model}

The shared model contains the game rules, the board state, and the physics data structures. \texttt{GameModel} determines match progression, while the physics engine is supplied by the launcher.

\subsection{Sequential baseline}

The sequential version advances the game on one thread. It serves as the reference point for validation and performance comparison.

\subsection{Platform-thread runtime}

The platform-thread version uses a controller/worker structure. The controller advances the match and publishes snapshots, whereas worker threads execute bounded physics work under controlled synchronization.

\subsection{Task-based runtime}

The task-based version follows the same ownership rule, but it expresses parallel work as executor tasks rather than long-lived workers. Tasks compute partial results, the controller merges them, and the new state is published only after the merge.

\subsection{Snapshots and view data}

The GUI reads immutable snapshots instead of the mutable board. Rendering remains separate from simulation and synchronization.

\subsection{Core modules}

The \texttt{model/common/math} package contains the immutable geometric primitives used throughout the project. The \texttt{model/physics/common} package contains the board, balls, holes, and the shared physics abstractions. The \texttt{model/game} package defines the game rules and the logical snapshots.

The physics implementations are split by execution strategy. \texttt{model/physics/sequential} provides the baseline stepping logic, \texttt{model/physics/threaded} contains the platform-thread engine, and \texttt{model/physics/taskbased} contains the executor-based engine.

The \texttt{runtime} package provides command queues, command receipts, snapshot publication, and bot coordination. The \texttt{view} package contains the Swing-facing classes that render immutable state.

\subsection{Important classes}

The principal classes are:

\begin{itemize}
\item \texttt{GameModel}: owns the game rules and advances the match state;
\item \texttt{Board}: owns the mutable physical state and delegates stepping to a physics engine;
\item \texttt{PhysicsEngine}, \texttt{ThreadedPhysicsEngine}, and \texttt{TaskBasedPhysicsEngine}: implement the simulation strategies;
\item \texttt{ThreadedGameRunner} and \texttt{TaskBasedGameRunner}: coordinate asynchronous commands, controller ticks, and snapshot publication;
\item \texttt{RuntimeGameSnapshot}: packages immutable state for the GUI and asynchronous observers;
\item \texttt{CommandQueueMonitorSupport} and \texttt{SnapshotStoreSupport}: implement the monitor-based coordination used by the concurrent runtime.
\end{itemize}

\subsection{Petri nets}

The behavior of the concurrent protocol can be described with an abstract Petri net. The model does not represent the full physics of the game; instead, it captures one simulation tick as a sequence of controlled phases. In particular, it represents command draining, ownership of the board during a tick, worker execution, barrier synchronization, and snapshot publication.

The resulting abstraction is small enough to reason about, but still expressive enough to justify the most relevant safety properties. A tick starts only when the controller owns the board and the command queue has been drained. Worker or task phases then execute on private work units or partial results, and the snapshot is published only after the merge and commit point has been reached. This captures the intended single-writer discipline of the concurrent runtime.

\subsection{JPF model checking}

The repository also includes minimal JPF harnesses in the verification area of the working tree. These harnesses are deliberately smaller than the production runtime: they model a controller, a bounded amount of worker or task activity, a command queue, and the publication step. The goal is to verify the control protocol, not the numerical physics engine.

The JPF models check that commands are not stranded, that publication happens after the tick is complete, and that the reduced protocol can terminate cleanly without deadlock. This is enough to validate the coordination pattern used by both the platform-thread and task-based implementations.

\section{Conclusions}

The repository contains a sequential implementation, a platform-thread implementation, and a task-based implementation. The shared domain model is reused across all three.

The code uses single-writer ownership, immutable snapshots, explicit synchronization, and a separation between model and runtime.

The benchmark data in the repository shows different speedup values across workloads and worker counts.
