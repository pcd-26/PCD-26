\section{Introduction}

Assignment 1 asks for a concurrent version of \emph{Poool} with two implementations: one based on platform threads and one based on the Executor framework. The assignment brief also asks for a sequential version, performance tests, and verification with model checking.

The delivered project contains three execution strategies:

\begin{itemize}
    \item a sequential baseline;
    \item a platform-thread implementation;
    \item a task-based implementation.
\end{itemize}

The source tree separates the shared game model from the execution strategy. The same domain rules are reused by the three launchers.

\section{Problem Analysis}

The game board contains many small balls and two cue balls, one for the human player and one for the bot. The rules described in the assignment brief are the following:

\begin{itemize}
    \item balls move, bounce, collide, and slow down because of friction;
    \item the board has holes in the top corners;
    \item when a player puts a small ball into a hole, that player's score increases;
    \item if a cue ball enters a hole, the other player wins;
    \item human and bot actions are asynchronous.
\end{itemize}

The concurrent part of the assignment requires controlled access to shared state. In this code base, \texttt{GameModel} is the authoritative state for game progression, while the runtime layer coordinates command submission and immutable snapshot publication.

\section{Design}

The code is organized into separate packages that separate domain logic, execution strategies, and presentation concerns. The main application modules under \texttt{src/main/java/pcd/poool} are the shared model, the runtime support layer, the sequential launcher, the platform-thread launcher and engine, the task-based launcher and engine, and the view layer.

\subsection{Shared model}

The shared model contains the game rules and the physics data structures. The implementation reuses the same model classes across the sequential, threaded, and task-based versions.

\subsection{Sequential baseline}

The sequential runtime owns a single \texttt{GameModel} and advances the board on one thread. It is the baseline used in the benchmark data.

\subsection{Platform-thread runtime}

The platform-thread implementation uses a controller/worker structure. The controller advances the match and the workers compute bounded pieces of the physics work. The runtime support classes include:

\begin{itemize}
    \item \texttt{CommandQueueMonitorSupport};
    \item \texttt{CommandReceiptSupport};
    \item \texttt{SnapshotStoreSupport};
    \item \texttt{WorkerCompletionMonitor}.
\end{itemize}

\subsection{Task-based runtime}

The task-based implementation uses the Executor framework. The controller serializes the match state, and the expensive work is split into tasks submitted to an executor.

\subsection{Snapshots and view data}

The GUI reads snapshot data rather than the mutable board directly. The view layer uses separate view model and snapshot classes.

\section{Implementation}

\subsection{Main launchers}

The project contains three main entry points:

\begin{itemize}
    \item \texttt{pcd.poool.SequentialPoool};
    \item \texttt{pcd.poool.ThreadedPoool};
    \item \texttt{pcd.poool.TaskBasedPoool}.
\end{itemize}

\subsection{Physics pipeline}

Each simulation tick follows the same sequence:

\begin{enumerate}
    \item collect the active balls;
    \item integrate movement and friction;
    \item apply boundary interactions and hole effects;
    \item build collision candidates;
    \item resolve collisions;
    \item commit the resulting state;
    \item publish a snapshot.
\end{enumerate}

The concurrent implementations parallelize the expensive portions of this pipeline and keep the merge and commit phases serialized.

\subsection{Project structure}

The source tree is organized into the following areas:

\begin{itemize}
    \item \texttt{model}: rules, physics, and domain objects;
    \item \texttt{runtime}: command queues and snapshot support;
    \item \texttt{sequential}: sequential execution entry points and baseline runtime;
    \item \texttt{threaded}: platform-thread orchestration;
    \item \texttt{taskbased}: executor-oriented orchestration;
    \item \texttt{view}: rendering and UI-facing view models;
    \item \texttt{verification}: JPF harnesses and Petri-net notes.
\end{itemize}

\section{Verification and Testing}

The repository includes JUnit tests under \texttt{src/test/java/pcd/poool}. The tests cover the game model, the physics engines, the runtime helpers, the view model, and the benchmark utilities.

The repository also includes JPF harnesses and Petri-net notes in the verification area of the working tree. These materials describe the concurrent coordination protocol at a smaller level of abstraction than the full simulation.

\section{Conclusions}

The repository contains a sequential implementation, a platform-thread implementation, and a task-based implementation. The shared domain model is reused across all three.

The code uses single-writer ownership, immutable snapshots, explicit synchronization, and a separation between model and runtime.

The benchmark data in the repository shows different speedup values across workloads and worker counts.
