\section{Introduction}

Assignment 1 requires three execution strategies for \emph{Poool}: a sequential baseline, a platform-thread implementation, and a task-based implementation built on the Executor framework. The brief also asks for performance measurements and verification with model checking.

The delivered project provides the following execution strategies:

\begin{itemize}
    \item \textbf{Sequential baseline}: single-thread reference execution;
    \item \textbf{Platform-thread version}: controller-led platform-thread architecture with long-lived workers;
    \item \textbf{Task-based version}: Executor-based parallel execution.
\end{itemize}

All three launchers reuse the same game rules.

\section{Problem Analysis}

The main difficulty is not the rule set itself, but the combination of shared mutable state, asynchronous activity, and a potentially heavy simulation workload. The board contains many balls that move, collide, and change status during the same tick, so the system must combine concurrency with deterministic state transitions.

\begin{itemize}
    \item \textbf{High computational cost}: collision detection and collision resolution dominate the simulation when the number of balls grows;
    \item \textbf{Shared mutable state}: the simulation must update the state consistently even when several events are active at the same time;
    \item \textbf{Asynchronous inputs}: human and bot actions may arrive while the simulation is running;
    \item \textbf{Deterministic behavior}: concurrency must not change the logical outcome of the match;
    \item \textbf{Responsiveness}: the interface must keep reacting while the simulation progresses.
\end{itemize}

The concurrent part of the assignment therefore becomes a question of identifying which parts of the simulation can be parallelized and which parts must remain serialized. For example, collision processing can be split across independent chunks, while processing pending commands must remain serialized because it requires a consistent global view of the match.

The key challenge is to exploit parallelism without breaking coherence.

\section{Design}

\noindent
The design separates responsibilities to keep the concurrent execution clear. The model owns the rules and the game state, the runtime advances the simulation, and the view reads only stable snapshots.

\begin{itemize}
    \item \textbf{Game logic}: rules and state transitions;
    \item \textbf{Runtime layer}: command handling and tick progression;
    \item \textbf{View layer}: immutable snapshots.
\end{itemize}

The same game logic is reused by the sequential, platform-thread, and task-based versions; only the execution strategy changes.

\subsection{Project architecture}

The project separates what must stay authoritative from what can be scheduled differently. The model keeps the match state and the rules, the runtime layer drives the simulation, serializes command handling, and coordinates asynchronous actions, while the view consumes only stable snapshots. In this way, the graphical side never depends on the internal timing of the simulation.

\begin{itemize}
    \item the model owns the rules and the authoritative state;
    \item the runtime coordinates commands and tick progression;
    \item the view reads snapshots only, never the live board.
\end{itemize}

The sequential version is the reference architecture. A single execution flow reacts to the input callbacks, advances the physics, updates the logical state, and publishes the resulting snapshot. This version is simple on purpose: it defines the expected semantics and provides the baseline used to evaluate the concurrent versions.

\subsection{Designing the concurrent solution}

The design idea is simple: each tick has a part that can be split across workers and a part that must stay under one controller. The parallel part is the expensive physics work; the serial part is the coordination that keeps the match coherent.

At design level, we do not yet care about how workers are implemented internally. We only care about the responsibilities of the phases: some phases read the current state and produce partial results, while other phases merge those results, apply the final state changes, and publish the next snapshot.

\begin{itemize}
    \item \textbf{Parallelizable}: local physics work over independent chunks of the simulation;
    \item \textbf{Not parallelizable}: command processing, merge/commit steps, score updates, game-over checks, and snapshot publication;
    \item \textbf{Design goal}: keep one coherent game state while letting the heavy local work run in parallel.
\end{itemize}

This separation is what makes the design effective. The concurrent versions avoid letting multiple threads contend on the same mutable state, and they do not force the whole simulation to wait on fine-grained synchronization. The price is that the local work must be joined again at the end of the tick, but that join is the exact point where the shared state becomes coherent again.

\subsection{Platform-thread version}

The platform-thread version uses one controller thread plus long-lived worker platform threads. The controller keeps ownership of the global progression of the match, while workers handle the parallelizable part of the physics workload. This gives the runtime a clear control point while still allowing the expensive simulation work to run concurrently.

\begin{itemize}
    \item the controller remains responsible for the global tick;
    \item workers handle bounded pieces of the physics workload;
    \item the controller also merges the partial results produced by the workers and applies the final state changes;
    \item the phase boundaries stay explicit, so the protocol remains deterministic.
\end{itemize}

\subsection{Task-based version}

The task-based version keeps a single controller thread for the serial phases of the tick, while the parallelizable physics work is expressed as executor tasks. The controller submits the tasks, waits for completion, merges the partial results, and publishes the final snapshot only after the merge is complete. The difference is mainly in how the concurrent work is represented and scheduled, and the task-based engine also keeps a fast path for small workloads where the single range is executed directly.

\begin{itemize}
    \item the controller keeps the serial phases of the tick;
    \item tasks compute the parallelizable physics work independently;
    \item the controller merges the partial results and publishes the next snapshot only after the merge is complete.
\end{itemize}

\subsection{Shared state and snapshots}

The model creates the logical game snapshot, while the runtime publishes the immutable runtime snapshot consumed by the view. This prevents rendering from seeing half-finished updates and gives the GUI a stable picture of the match at each publication point.

\subsection{Why this design works}

The improvement does not come from changing the game rules, but from reducing coordination overhead around the same rules. As the number of balls grows, the amount of parallelizable physics work grows as well, so the concurrent versions can better exploit the available cores on larger workloads.

\section{Implementation}

\subsection{Implementation overview}

The implementation mirrors the design: the same game rules are reused by all launchers, while the execution strategy changes between the sequential, platform-thread, and task-based versions. The code is organized into separate packages for the model, the physics engines, the runtime helpers, and the Swing view, so the responsibilities remain visible in the source tree as well as in the report.

The core of the project is the way the concurrent physics engines divide, compute, and join work. Intuitively, the controller first decides which balls each worker should look at, then the workers do the expensive local physics work, and finally the controller gathers the partial results and commits them to the shared board. The workers never become owners of the global state: they work on private slices, produce partial results, and hand them back for a deterministic join.

This is the actual staged pipeline used in both concurrent engines:

\begin{enumerate}
    \item the active balls are split into \textbf{contiguous index ranges};
    \item each worker integrates the movement of its own range, so the ball positions are updated before any collision work starts;
    \item hole interactions are applied serially on the authoritative board, because that part must stay globally ordered;
    \item the remaining balls are projected into private \textbf{center-cell grids}, one per worker/task;
    \item the controller merges those local grids into one deterministic occupied-cell view;
    \item the occupied cells are sorted, so each cell is resolved in a stable order;
    \item each worker resolves the cells it owns, computes the collision contribution for the relevant ball pairs, and stores the effect in a sparse private accumulator;
    \item the controller merges the sparse accumulators and applies the final board writes only after the join barrier completes.
\end{enumerate}

The same structure appears in both concurrent engines:

\begin{itemize}
    \item \textbf{range partitioning}: the list of active balls is split into almost equal \textbf{contiguous chunks}, one per worker or task;
    \item \textbf{private local grids}: each worker builds its own center-cell map for the balls in its range;
    \item \textbf{deterministic merge}: the controller merges the local grids into one ordered view of the occupied cells;
    \item \textbf{owned-cell resolution}: each occupied cell is resolved once, together with a fixed set of forward neighbors, so each relevant pair is considered exactly once;
    \item \textbf{sparse final commit}: workers accumulate deltas locally, the coordinator merges them, and the final board writes happen only after the join barrier completes.
\end{itemize}

The threaded engine implements the barriers with long-lived platform workers and a completion monitor. The task-based engine uses the same staged logic, but it submits each range to an executor and waits on `Future`s instead of worker joins. The task-based engine also keeps a small-workload fast path: when the workload is too small to justify parallel decomposition, it executes the single range directly instead of paying executor overhead.

This keeps collision handling \textbf{deterministic}, avoids \textbf{duplicate writes}, and still lets the \textbf{expensive physics work} run in parallel. In other words, the workers compute the physics, while the coordinator preserves a \textbf{single authoritative state} and commits the final outcome.

\begin{itemize}
    \item \textbf{\texttt{pcd.poool.model}}: game rules, board state, and immutable snapshots;
    \item \textbf{\texttt{pcd.poool.model.physics}}: sequential, threaded, and task-based physics engines;
    \item \textbf{\texttt{pcd.poool.runtime}}: command submission and snapshot publication helpers;
    \item \textbf{\texttt{pcd.poool.threaded}} and \textbf{\texttt{pcd.poool.taskbased}}: concurrent runners;
    \item \textbf{\texttt{pcd.poool.view}}: rendering and input handling.
\end{itemize}

The three public entry points are \texttt{SequentialPoool}, \texttt{ThreadedPoool}, and \texttt{TaskBasedPoool}. They build the corresponding runtime, connect it to the view, and keep the GUI loop separate from the simulation logic.

\subsection{Core classes}

\begin{itemize}
    \item \texttt{GameModel} (\texttt{pcd.poool.model.game}): owns the gameplay rules, scoring, end-game conditions, and logical snapshot creation;
    \item \texttt{Board} (\texttt{pcd.poool.model.physics.common}): owns the mutable physical state and delegates stepping to a \texttt{PhysicsStepper};
    \item \texttt{SequentialPhysicsEngine} (\texttt{pcd.poool.model.physics.sequential}), \texttt{ThreadedPhysicsEngine} (\texttt{pcd.poool.model.physics.threaded}), and \texttt{TaskBasedPhysicsEngine} (\texttt{pcd.poool.model.physics.taskbased}): implement the sequential, platform-thread, and executor-based physics pipelines;
    \item \texttt{ThreadedGameRunner} (\texttt{pcd.poool.threaded}) and \texttt{TaskBasedGameRunner} (\texttt{pcd.poool.taskbased}): coordinate command draining, controller ticks, and snapshot publication;
    \item \texttt{RuntimeGameSnapshot} (\texttt{pcd.poool.runtime}): packages the logical snapshot together with the immutable render data;
    \item \texttt{CommandQueueMonitorSupport} and \texttt{SnapshotStoreSupport} (\texttt{pcd.poool.runtime}): provide the monitor-based communication used by the concurrent runtimes.
\end{itemize}

The most relevant point is that \texttt{GameModel} remains the authoritative owner of the game rules, while the runners only coordinate access to it. This keeps the same behavior across all variants and avoids duplicating the domain logic.

\subsection{Sequential implementation}

The sequential launcher is intentionally direct: one loop advances the simulation, updates the view model, and renders the frame. The game model and the view share the same object graph, but the simulation still remains easy to reason about because everything happens in order.

The helper \texttt{advanceGame} only guards the finished-state check: \texttt{GameModel.step()} advances the board through \texttt{Board.updateState()}, then consumes score events and refreshes the game status.

\begin{lstlisting}[style=codestyle,caption={Sequential main loop},label={lst:sequential-main-loop}]
var game = gameRef.get();
long elapsedMillis = Math.max(PhysicsDefaults.FIXED_STEP_MILLIS, now - lastUpdateTime);
lastUpdateTime = now;

advanceGame(game, elapsedMillis);
if (game.canBotShoot()) {
    if (botAimStartedAt == 0) {
        botAimStartedAt = now;
    } else if (now - botAimStartedAt >= BOT_THINK_TIME_MILLIS) {
        game.shootBot();
        viewModel.clearShotPreview(Player.BOT);
        botAimStartedAt = 0;
    }
} else {
    viewModel.clearShotPreview(Player.BOT);
    botAimStartedAt = 0;
}

renderedFrames++;
int currentFramesPerSecond = getCurrentFPS(renderedFrames, startTime, now);
viewModel.update(game.board(), game.snapshot(), currentFramesPerSecond);
updateBotShotPreview(game, viewModel, botAimStartedAt > 0);
view.render();
\end{lstlisting}

\noindent\textit{Source: \texttt{assignment-1/src/main/java/pcd/poool/SequentialPoool.java}, lines 61--82.}

This version is useful as the semantic baseline. It defines the expected behavior of the game without introducing concurrency concerns, and it also shows the minimum amount of code needed to keep the GUI responsive.

\subsection{Platform-thread implementation}

The platform-thread version introduces a controller thread plus an optional bot thread. The controller is the only thread that mutates the model, while external producers submit commands through a monitor-backed queue. The threaded physics engine is still called from the controller, so the controller remains the single point where the match advances.

\begin{lstlisting}[style=codestyle,caption={Threaded controller loop},label={lst:threaded-controller-loop}]
while (running) {
    drainPendingCommands();
    if (!game.snapshot().isFinished()) {
        game.step(config.tickMillis());
    }
    snapshots.publish(RuntimeGameSnapshot.from(game));
    sleepTick();
}
\end{lstlisting}

The key classes here are \texttt{ThreadedGameRunner} and \texttt{ThreadedPhysicsEngine}. The runner serializes the game protocol, and the threaded physics engine parallelizes the expensive simulation work internally. The most explicit handoff happens inside \texttt{runRanges()}, where the controller assigns one range of work to each worker thread.

\begin{lstlisting}[style=codestyle,caption={Range partitioning for worker assignment},label={lst:threaded-range-partition}]
int workerCount = Math.min(workers.length, itemCount);
int baseChunk = itemCount / workerCount;
int remainder = itemCount % workerCount;
int from = 0;
for (int workerIndex = 0; workerIndex < workerCount; workerIndex++) {
    int chunkSize = baseChunk + (workerIndex < remainder ? 1 : 0);
    int start = from;
    int end = start + chunkSize;
    int assignedWorker = workerIndex;
    workers[workerIndex].assign(() -> rangeTask.run(start, end, assignedWorker), completion);
    from = end;
}
\end{lstlisting}

\noindent\textit{Source: \texttt{assignment-1/src/main/java/pcd/poool/model/physics/threaded/ThreadedPhysicsEngine.java}, lines 544--568.}

This is the part that decides how the balls are split among workers: the work is divided into contiguous index ranges of almost equal size, with the remainder distributed among the first workers.

In other words, a ball is assigned to the chunk identified by its position in \texttt{activeBalls}: the worker does not receive spatial zones, but a contiguous slice of the list, and it processes every ball in that slice in order. The collision phase follows the same pattern: each worker computes local contributions on its own slice, builds a private spatial view, and resolves the cells it owns before the controller merges the sparse results and applies the final writes to the authoritative board.

\begin{lstlisting}[style=codestyle,caption={Threaded handoff from controller to workers},label={lst:threaded-handoff}]
for (int workerIndex = 0; workerIndex < workerCount; workerIndex++) {
    int chunkSize = baseChunk + (workerIndex < remainder ? 1 : 0);
    int start = from;
    int end = start + chunkSize;
    int assignedWorker = workerIndex;
    workers[workerIndex].assign(() -> rangeTask.run(start, end, assignedWorker), completion);
    from = end;
}

completion.await();
\end{lstlisting}

\noindent\textit{Source: \texttt{assignment-1/src/main/java/pcd/poool/model/physics/threaded/ThreadedPhysicsEngine.java}, lines 562--578.}

This is the actual point where the controller passes the physics work to the worker threads. The workers run their assigned range independently, and the controller resumes only after the completion barrier has been reached.

The collision phase then follows the same idea on top of this handoff: each worker computes local contributions on its own slice, builds a private spatial view, and resolves the cells it owns. The controller only merges the sparse results and applies the final writes to the authoritative board.

\subsection{Task-based implementation}

The task-based version keeps the same controller-driven protocol, but the parallel physics phase is expressed as executor tasks. The runner uses a scheduled single-thread controller executor for the tick and a separate executor for the bot when enabled. The task-based physics engine still splits the active balls into contiguous ranges, but each range is submitted as a task rather than assigned to a long-lived worker thread.

\begin{lstlisting}[style=codestyle,caption={Task-based controller scheduling},label={lst:taskbased-scheduling}]
running = true;
controllerExecutor.scheduleAtFixedRate(this::tick, 0,
        config.tickMillis(), TimeUnit.MILLISECONDS);
\end{lstlisting}

\begin{lstlisting}[style=codestyle,caption={Task-based range partitioning},label={lst:taskbased-range-partition}]
int workerCount = itemCount < MIN_ITEMS_FOR_PARALLEL_RANGES ? 1 : Math.min(poolSize, itemCount);
int baseChunk = itemCount / workerCount;
int remainder = itemCount % workerCount;
var chunks = new ArrayList<RangeChunk>(workerCount);
int from = 0;
for (int i = 0; i < workerCount; i++) {
    int chunkSize = baseChunk + (i < remainder ? 1 : 0);
    int to = from + chunkSize;
    chunks.add(new RangeChunk(from, to, i));
    from = to;
}
\end{lstlisting}

\noindent\textit{Source: \texttt{assignment-1/src/main/java/pcd/poool/model/physics/taskbased/TaskBasedPhysicsEngine.java}, lines 662--672.}

Inside the task-based physics engine, the work is partitioned into ranges and executed through futures. This keeps the concurrency model explicit: tasks do the independent work, the coordinator waits, and only then are the shared updates applied. For collision detection, each task builds a private local grid, the coordinator merges those grids, sorts the packed candidate pairs, records collisions in deterministic order, and only then applies the accumulated deltas. The shared idea is still the same single-writer ownership rule; what changes is that futures replace worker joins and candidate pairs are materialized explicitly before replay.

\begin{lstlisting}[style=codestyle,caption={Task submission and synchronization},label={lst:taskbased-futures}]
var futures = new ArrayList<Future<T>>(ranges.size());
for (var range : ranges) {
    futures.add(executor.submit(() ->
            rangeTask.run(range.fromInclusive(), range.toExclusive(),
                    range.workerIndex())));
}
for (var future : futures) {
    results.add(future.get());
}
\end{lstlisting}

Compared with the threaded implementation, the control protocol is almost the same from the report point of view. What changes is the execution style: long-lived workers on one side, scheduled tasks on the other. The shared idea is still the same single-writer ownership rule.

\subsection{Runtime snapshots and coordination helpers}

\texttt{RuntimeGameSnapshot} is the bridge between the model and the GUI. It combines the logical \texttt{GameSnapshot} with the copied board and preview data used by the view, so rendering never needs to inspect mutable state directly.

\begin{lstlisting}[style=codestyle,caption={Runtime snapshot construction},label={lst:runtime-snapshot}]
return new RuntimeGameSnapshot(
        game.snapshot(),
        List.copyOf(board.getBalls()),
        board.getPlayerBall(),
        board.getBotBall(),
        List.copyOf(board.getHoles()),
        game.previewBotShot());
\end{lstlisting}

The concurrent runners publish those snapshots through \texttt{SnapshotStoreSupport}, which acts as a simple monitor around the latest immutable state. Commands follow the same idea through \texttt{CommandQueueMonitorSupport}: external threads enqueue requests, and the controller drains them sequentially.

\subsection{Implementation summary}

Overall, the implementation keeps the domain model small and central, pushes concurrency into the runtime and physics layers, and uses immutable snapshots to isolate the view. The result is a code base where the sequential, threaded, and task-based versions differ mainly in scheduling, not in game semantics.

\subsection{Petri nets}

The concurrent protocol can be described with an abstract Petri net. The purpose of the model is not to represent the full physics of the game, but to capture one simulation tick as a sequence of controlled phases. In particular, it records command draining, board ownership, worker execution, barrier synchronization, and snapshot publication.

The abstraction is small enough to reason about, yet expressive enough to justify the most relevant safety properties. A tick starts only when the controller owns the board and the command queue has been drained. Worker or task phases then execute on private work units or partial results, and the snapshot is published only after the merge and commit point has been reached. This captures the intended single-writer discipline of the concurrent runtime.

\begin{itemize}
    \item \textbf{What is modeled}: one simulation tick as a sequence of controlled phases;
    \item \textbf{What is not modeled}: full physics, numerical details, GUI rendering;
    \item \textbf{Phases captured}: command draining, board ownership, worker execution, barrier synchronization, snapshot publication;
    \item \textbf{Safety intuition}: the tick starts only when the controller owns the board, and publication happens only after merge and commit.
\end{itemize}

\subsection{JPF model checking}

The repository also includes minimal JPF harnesses in the verification area of the working tree. These harnesses are deliberately smaller than the production runtime: they model a controller, a bounded amount of worker or task activity, a command queue, and the publication step. The goal is to verify the control protocol, not the full numerical physics behavior.

The JPF models check that commands are not stranded, that publication happens after the tick is complete, and that the reduced protocol can terminate cleanly without deadlock. This is enough to validate the coordination pattern used by both the platform-thread and task-based implementations.

\begin{itemize}
    \item \textbf{Harnesses}: minimal JPF models in the verification area of the working tree;
    \item \textbf{Scope}: controller, bounded worker/task activity, command queue, publication step;
    \item \textbf{Goal}: verify the control protocol, not the full numerical physics behavior;
    \item \textbf{Properties checked}: no stranded commands, publication after tick completion, clean termination without deadlock.
\end{itemize}

\section{Conclusions}

The repository contains a sequential implementation, a platform-thread implementation, and a task-based implementation. The shared domain model is reused across all three.

The code uses single-writer ownership, immutable snapshots, explicit synchronization, and a separation between model and runtime.

The benchmark data in the repository shows different speedup values across workloads and worker counts.
