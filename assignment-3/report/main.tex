\begin{abstract}
This report presents the complete formal analysis, architectural design, software implementation, and empirical verification of Assignment 3 for the Concurrent and Distributed Systems course (A.Y. 2025--2026). The assignment investigates two fundamental message-passing paradigms for concurrent software development: \emph{asynchronous actor-based message passing} and \emph{synchronous process-based channel communication}. 

Subexercise \#1 implements a reactive \emph{Smart Home Alarm System} (SHAS) in Java 21 using the Apache Pekko Typed framework. The control unit is modeled as an encapsulated finite state machine (FSM) featuring configurable exit and entry countdown timers, single-shot timeout scheduling, and a bonus extension for zone-based partial arming (Night Mode vs. Full Arming). Subexercise \#2 implements a single-elimination \emph{Heads-or-Tails Championship} (HOTC) in Go 1.22, leveraging lightweight goroutines and channels under Communicating Sequential Processes (CSP) principles to coordinate parallel tournament rounds without shared mutable memory. 

Both subprojects feature rigorous automated test suites (49 unit/integration tests for SHAS and 35 test scenarios for HOTC). Concurrency correctness proofs—including custom multi-channel barrier verification for goroutine synchronization and Pekko virtual-time actor testing—demonstrate complete deadlock freedom, deterministic bracket ordering, and resilience against state race conditions. Finally, we provide a deep quantitative and qualitative comparison between the Actor and CSP concurrency models.
\end{abstract}

\section{Introduction and Theoretical Foundations}

Concurrent and distributed software engineering relies fundamentally on message passing as an alternative to shared-memory concurrency with explicit locking. Shared mutable state synchronized via primitives such as mutexes, semaphores, or condition variables often introduces subtle bug vectors including deadlocks, priority inversions, memory visibility issues, and race conditions. Message passing replaces shared state with autonomous concurrent entities that communicate exclusively via explicit message exchanges. 

This assignment evaluates two dominant message-passing models:
\begin{enumerate}[leftmargin=*]
    \item \textbf{The Actor Model:} Pioneered by Hewitt, Bishop, and Steiger (1973) and formalized by Agha (1986), where encapsulated entities (actors) process messages sequentially from private mailboxes and modify internal state through behavior substitution.
    \item \textbf{Communicating Sequential Processes (CSP):} Formulated by Hoare (1978), where independent sequential processes communicate over explicit, synchronized (or buffered) communication channels.
\end{enumerate}

To contrast these abstractions in practical, enterprise-grade ecosystems, Subexercise \#1 implements an event-driven \emph{Smart Home Alarm System} (SHAS) using Java 21 and Apache Pekko Typed 1.0. Subexercise \#2 implements a parallel \emph{Heads-or-Tails Championship} (HOTC) using Go 1.22 standard channels and goroutines.

\subsection{Theoretical Background: The Actor Model}

In the Actor Model, the fundamental unit of computation is the \emph{Actor}. An actor encapsulates state, behavior, a mailbox, and execution context. When an actor processes a message, it can perform three basic operations:
\begin{enumerate}
    \item Send a finite number of messages to other actors whose addresses are known to it;
    \item Create a finite number of new actors;
    \item Designate the behavior $B_{n+1}$ to be used for processing the next incoming message in its mailbox.
\end{enumerate}

Formally, an actor system can be defined as a set of autonomous state machines. Let $A$ be an actor with address $\alpha$, state space $S$, and mailbox queue $Q \subseteq M^*$. The processing of a message $m \in Q$ under current behavior $B_i: S \times M \to S \times \mathcal{P}(A) \times M^*$ is atomic:
\begin{equation}
(S_i, m) \xrightarrow{B_i} (S_{i+1}, A_{\text{new}}, M_{\text{out}})
\end{equation}

Crucially, state mutation is completely localized within the actor. Because messages are processed sequentially from the actor's mailbox queue $Q$, no two threads ever mutate $S$ concurrently, eliminating the need for synchronized blocks or lock acquisition inside the domain logic. In Apache Pekko Typed, this model is further enhanced by strong static typing: actor references are parameterized by the message protocol $\text{ActorRef}<T>$, ensuring at compile time that an actor receives only messages it is designed to handle.

\subsection{Theoretical Background: Communicating Sequential Processes (CSP)}

Communicating Sequential Processes (CSP) focuses on processes and channels rather than entity identities. In CSP, concurrent computations consist of independent sequential processes $P_1, P_2, \dots, P_k$ that synchronize through explicit communication channels. 

A channel $c$ serves as a communication conduit between sender $P_s$ and receiver $P_r$. In unbuffered (synchronous) channels, message transfer enforces barrier synchronization:
\begin{equation}
P_s: c ! v \quad \parallel \quad P_r: x \leftarrow c
\end{equation}

Neither process can proceed past the transfer point until both sender and receiver are ready, completing an instant rendezvous. In buffered channels, senders proceed asynchronously until the channel buffer capacity $C$ is exhausted, at which point the sender blocks until capacity becomes available.

In Go, CSP is implemented via \emph{goroutines} (lightweight user-space threads managed by an $M:N$ scheduler) and typed channels (\texttt{chan T}). Go's proverb \emph{"Do not communicate by sharing memory; instead, share memory by communicating"} directly reflects CSP principles.

\subsection{Subexercise \#1: Smart Home Alarm System (SHAS)}

The Smart Home Alarm System manages physical security hardware across residential premises. The system consists of four primary entity types:
\begin{itemize}[leftmargin=*]
    \item \textbf{Keypad Terminal:} Accepts numerical PIN inputs, clear/submit keypresses, and arming mode selections (\texttt{ArmAll}, \texttt{ArmPartial}).

\subsubsection{Bonus Extension: Zone-Based Partial Arming}

In real-world security systems, occupants frequently require partial perimeter arming (e.g., Night Mode). The SHAS bonus extension partitions physical space into five distinct zones:
\begin{equation}
Z_{\text{all}} = \{\text{PERIMETER}, \text{LIVING\_AREA}, \text{SLEEPING\_AREA}, \text{GROUND\_FLOOR}, \text{UPPER\_FLOOR}\}
\end{equation}

When arming, occupants can issue an \texttt{ArmPartial($Z_{\text{active}}$)} command where $Z_{\text{active}} \subseteq Z_{\text{all}}, Z_{\text{active}} \neq \emptyset$. During the \texttt{ARMED} state, sensor activations produce an intrusion trigger if and only if the sensor's assigned zone belongs to the currently active set:
\begin{equation}
\text{TriggerIntrusion}(s) = \begin{cases} 
\text{True} & \text{if } \text{Zone}(s) \in Z_{\text{active}} \\ 
\text{False} & \text{if } \text{Zone}(s) \notin Z_{\text{active}} 
\end{cases}
\end{equation}

Sensors in inactive zones (e.g., movement in \texttt{SLEEPING\_AREA} during Night Mode) are safely ignored, preventing false alarms.

\subsection{Subexercise \#2: Heads-or-Tails Championship (HOTC)}

The Heads-or-Tails Championship simulates a single-elimination coin-toss tournament among $N = 2^m$ players across $m = \log_2 N$ rounds.

\subsubsection{Mathematical Structure}

A tournament with $N$ players requires:
\begin{equation}
M_{\text{total}} = \sum_{k=1}^{m} \frac{N}{2^k} = N - 1 \quad \text{total matches}
\end{equation}

In round $k \in \{1, 2, \dots, m\}$, exactly $N / 2^k$ matches take place concurrently. Each match pairs two players $(P_{2j-1}, P_{2j})$ for $j \in \{1, \dots, N/2^k\}$. The coin toss produces an outcome $C \in \{\text{Heads}, \text{Tails}\}$. Player 1 wins if $C = \text{Heads}$, and Player 2 wins if $C = \text{Tails}$.

\subsubsection{Concurrency and Ordering Constraints}

The CSP implementation must satisfy three strict system invariants:
\begin{enumerate}
    \item \textbf{Intra-Round Concurrency:} All $N/2^k$ matches within round $k$ must execute concurrently in parallel goroutines.
    \item \textbf{Inter-Round Barrier Synchronization:} Round $k+1$ cannot spawn any match until all $N/2^k$ matches of round $k$ have concluded and yielded valid results.
    \item \textbf{Deterministic Bracket Placement:} Because goroutine scheduling is non-deterministic, match completion order may differ from match creation order. The coordinator must aggregate outcomes by bracket index (\texttt{matchIndex}) to preserve exact tournament bracket hierarchy.
\end{enumerate}

\section{Implementation Details}

\subsection{Exercise \#1 Implementation (Java 21 / Apache Pekko Typed)}

The central state machine is defined in \texttt{ControlUnitActor.java}. State behaviors are expressed as static methods returning \texttt{Behavior<Command>}. State parameters—such as the configured PIN, delay durations, typed siren reference, and active zone set—are passed immutably across behavior transitions.

Listing~\ref{lst:control-unit-full} illustrates the behavior handlers for the \texttt{DISARMED}, \texttt{EXIT\_DELAY}, and \texttt{ARMED} states.

\begin{lstlisting}[language=Java, caption={State transition handlers in ControlUnitActor.java}, label={lst:control-unit-full}]
private static Behavior<Command> disarmed(
    ActorContext<Command> context,
    TimerScheduler<Command> timers,
    String configuredPin,
    Duration exitDelayDuration,
    Duration entryDelayDuration,
    ActorRef<SirenActor.Command> siren,
    Set<Zone> selectedZones
) {
    return Behaviors.receive(Command.class)
        .onMessage(ArmAll.class, message -> {
            context.getLog().info("Configuring full arming");
            return disarmed(context, timers, configuredPin, exitDelayDuration, entryDelayDuration, siren, FULL_ARMS);
        })
        .onMessage(ArmPartial.class, message -> {
            context.getLog().info("Configuring partial arming for zones {}", message.activeZones());
            return disarmed(context, timers, configuredPin, exitDelayDuration, entryDelayDuration, siren, message.activeZones());
        })
        .onMessage(PinSubmitted.class, message -> {
            if (configuredPin.equals(message.pin())) {
                context.getLog().info("Transition DISARMED -> EXIT_DELAY");
                timers.startSingleTimer(EXIT_DELAY_TIMER_KEY, new ExitDelayTimeout(), exitDelayDuration);
                return exitDelay(context, timers, configuredPin, exitDelayDuration, entryDelayDuration, siren, selectedZones);
            }
            return ignorePinSubmission(context, AlarmState.DISARMED);
        })
        .onMessage(SensorActivated.class, message -> ignoreSensorActivation(context, AlarmState.DISARMED, message.sensorInfo()))
        .onMessage(QueryState.class, message -> replyState(message.replyTo(), AlarmState.DISARMED))
        .build();
}

private static Behavior<Command> armed(
    ActorContext<Command> context,
    TimerScheduler<Command> timers,
    String configuredPin,
    Duration exitDelayDuration,
    Duration entryDelayDuration,
    ActorRef<SirenActor.Command> siren,
    Set<Zone> activeZones
) {
    return Behaviors.receive(Command.class)
        .onMessage(PinSubmitted.class, message -> {
            if (configuredPin.equals(message.pin())) {
                context.getLog().info("Transition ARMED -> DISARMED");
                timers.cancel(ENTRY_DELAY_TIMER_KEY);
                siren.tell(new SirenActor.Deactivate());
                return disarmed(context, timers, configuredPin, exitDelayDuration, entryDelayDuration, siren, FULL_ARMS);
            }
            return ignorePinSubmission(context, AlarmState.ARMED);
        })
        .onMessage(SensorActivated.class, message -> {
            SensorInfo sensorInfo = message.sensorInfo();
            if (activeZones.contains(sensorInfo.zone())) {
                context.getLog().info("Transition ARMED -> ENTRY_DELAY (sensor={}, zone={})", sensorInfo.id(), sensorInfo.zone());
                timers.startSingleTimer(ENTRY_DELAY_TIMER_KEY, new EntryDelayTimeout(), entryDelayDuration);
                return entryDelay(context, timers, configuredPin, exitDelayDuration, entryDelayDuration, siren, activeZones);
            }
            return ignoreInactiveZone(context, sensorInfo);
        })
        .onMessage(QueryState.class, message -> replyState(message.replyTo(), AlarmState.ARMED))
        .build();
}
\end{lstlisting}

\subsubsection{Keypad Input Buffering}

The \texttt{KeypadActor} processes character keypresses incrementally. Listing~\ref{lst:keypad-impl} highlights the digit buffering, clear (\texttt{*}), and submit (\texttt{\#}) handling logic.

\begin{lstlisting}[language=Java, caption={Keypress decoding and submission in KeypadActor.java}, label={lst:keypad-impl}]
private Behavior<Command> onPressKey(PressKey command) {
    char key = command.key();
    if (Character.isDigit(key)) {
        pinBuffer.append(key);
        return this;
    }
    if (key == '#') {
        submitBufferedPin();
        return this;
    }
    if (key == '*') {
        pinBuffer.setLength(0);
    }
    return this;
}

private void submitBufferedPin() {
    if (pinBuffer.isEmpty()) return;
    String pin = pinBuffer.toString();
    getContext().getLog().info("Keypad submitting buffered PIN event");
    controlUnit.tell(new ControlUnitActor.PinSubmitted(pin));
    pinBuffer.setLength(0);
}
\end{lstlisting}

\subsection{Exercise \#2 Implementation (Go 1.22)}

The Go round coordinator \texttt{PlayRound} executes matches concurrently by launching goroutines and aggregating outcomes over an unbuffered outcome channel.

Listing~\ref{lst:go-round-impl} provides the complete implementation of \texttt{PlayRound} from \texttt{round.go}.

\begin{lstlisting}[language=Go, caption={Concurrent match execution and result aggregation in round.go}, label={lst:go-round-impl}]
type matchOutcome struct {
    matchIndex int
    result     MatchResult
    err        error
}

func PlayRound(round int, players []Player, tosserFactory CoinTosserFactory) ([]Player, []MatchResult, error) {
    matchCount := len(players) / 2
    outcomes := make(chan matchOutcome)

    for matchIndex := 0; matchIndex < matchCount; matchIndex++ {
        matchNumber := matchIndex + 1
        firstPlayer := players[matchIndex*2]
        secondPlayer := players[matchIndex*2+1]
        tosser := tosserFactory(round, matchNumber, firstPlayer, secondPlayer)

        go func(matchIndex, matchNumber int, firstPlayer, secondPlayer Player, tosser CoinTosser) {
            if tosser == nil {
                outcomes <- matchOutcome{matchIndex: matchIndex, err: fmt.Errorf("coin tosser must not be nil")}
                return
            }
            result, err := PlayMatch(round, matchNumber, tosser, firstPlayer, secondPlayer)
            outcomes <- matchOutcome{matchIndex: matchIndex, result: result, err: err}
        }(matchIndex, matchNumber, firstPlayer, secondPlayer, tosser)
    }

    orderedResults := make([]MatchResult, matchCount)
    var firstErr error
    for received := 0; received < matchCount; received++ {
        outcome := <-outcomes
        orderedResults[outcome.matchIndex] = outcome.result
        if outcome.err != nil && firstErr == nil {
            firstErr = outcome.err
        }
    }

    if firstErr != nil {
        return nil, nil, firstErr
    }

    winners := make([]Player, matchCount)
    for matchIndex, result := range orderedResults {
        winners[matchIndex] = result.Winner()
    }
    return winners, orderedResults, nil
}

\subsection{Exercise \#2 Verification (Go Test and Concurrency Proofs)}

Subexercise \#2 includes \textbf{35 test cases} written in Go. To prove concurrency invariants empirically, \texttt{concurrency\_test.go} implements a specialized multi-channel synchronization primitive called \texttt{coordinatedTosser}.

Listing~\ref{lst:coordinated-tosser} illustrates how \texttt{coordinatedTosser} blocks match workers using \texttt{started}, \texttt{done}, and \texttt{release} channels.

\begin{lstlisting}[language=Go, caption={Empirical concurrency test harness in concurrency\_test.go}, label={lst:coordinated-tosser}]
type coordinatedTosser struct {
    matchNumber int
    side        CoinSide
    started     chan<- int
    done        chan<- int
    release     <-chan struct{}
}

func (t coordinatedTosser) Toss() CoinSide {
    t.started <- t.matchNumber // Signal match startup
    <-t.release                 // Block until harness releases match
    t.done <- t.matchNumber    // Signal completion
    return t.side
}
\end{lstlisting}

\subsubsection{Empirical Concurrency Invariants Verified}

The Go test suite proves four critical concurrency invariants:
\begin{enumerate}
    \item \textbf{Simultaneous Match Startup:} Test \texttt{TestPlayRoundStarts}\allowbreak\texttt{EachMatchOnceAndWaitsForAllResults} proves that all match goroutines in a round send to \texttt{started} before any goroutine is released, confirming parallel dispatch.
    \item \textbf{Barrier Blocking:} The test asserts that \texttt{PlayRound} does not return until every worker goroutine has been released and yielded its result.
    \item \textbf{Bracket Order Preservation:} Test \texttt{TestPlayRoundPreserves}\allowbreak\texttt{OrderingWhenResultsCompleteOutOfOrder} releases match 2 before match 1. The test verifies that \texttt{orderedResults[0]} contains match 1 and \texttt{orderedResults[1]} contains match 2, proving that completion timing does not corrupt tournament brackets.
    \item \textbf{Goroutine Leak Freedom:} Test \texttt{TestPlayRoundPropagates}\allowbreak\texttt{ErrorWithoutBlockingGoroutines} verifies that invalid toss outputs propagate errors without abandoning uncollected goroutines on channel writes.
\end{enumerate}

\section{Comparative Analysis and Discussion}

\subsection{Architectural Trade-offs: Actor Model vs. CSP}

The implementation of SHAS and HOTC highlights key differences between Actor-based and CSP-based messaging:

\begin{enumerate}[leftmargin=*]
    \item \textbf{State Isolation vs. Synchronous Rendezvous:} In Pekko Actors, state is permanently bound to an actor instance. All interactions occur asynchronously via mailboxes. This model excels in long-lived reactive systems (e.g., security control units) where event sequences drive state behavior over extended periods. In CSP, goroutines are transient tasks. State is passed cleanly through channels as immutable value objects, which is ideal for data pipeline processing and parallel round execution.
    \item \textbf{Resource Overhead:} Pekko actors require JVM memory allocation for actor context, behavior instances, and mailbox queues. In contrast, Go goroutines begin with a minimal $2\text{ KB}$ stack size, allowing hundreds of thousands of goroutines to run concurrently with negligible footprint.
    \item \textbf{Ergonomics and Type Safety:} Java 21 sealed interfaces (\texttt{public interface Command}) combined with record patterns provide strong compile-time guarantees for actor protocols. Go relies on lightweight structural interfaces (\texttt{CoinTosser}) and explicit channel types (\texttt{chan matchOutcome}).
    \item \textbf{Fault Tolerance:} Pekko provides built-in supervision trees where parent actors monitor, restart, or resume failing child actors. In Go, error handling is explicit: errors are passed across channels as struct fields (\texttt{matchOutcome.err}) and handled directly by receiving processes.
\end{enumerate}
